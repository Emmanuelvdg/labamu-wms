Advanced Picking & Multi‑Step Workflows – Product Requirements Document Background The current Labamu WMS supports batch, cluster and wave picking strategies on the back‑end and has a workflow engine that can orchestrate put‑away and pick operations via specialised handlers . However, the front‑end only exposes a single‑order picking session, and the Routes module still defines simple one‑step "pull" rules without a graphical way to configure multi‑step sequences. The backlog also notes that waveless (continuous‑flow) picking is planned but not yet implemented. This gap means warehouse managers cannot take advantage of advanced fulfilment strategies such as batch/cluster/ wave picking, QC inspection or staging steps during inbound and outbound workflows, or dynamic routing that adapts to real‑time conditions. Purpose This PRD defines the functionality required to expose advanced picking strategies and multi‑step workflows in the Labamu WMS UI, and to implement waveless continuous flow picking. By closing this gap, operations teams will be able to configure and execute complex fulfilment scenarios – such as wave picking with consolidation, QC inspection before put‑away, or staged packing – directly from the user interface. The goal is to ensure parity between the back‑end capabilities and the front‑end experience, thereby improving productivity, reducing travel time and enabling dynamic re‑sequencing based on real‑time conditions. Goals & Objectives Expose advanced picking strategies in the UI  – Allow operators to start picking sessions with batch, cluster, wave and waveless strategies. Provide controls to group orders by destination, product type, shipping cut‑off or other criteria. Implement waveless (continuous‑flow) picking  – Extend the  PickingStrategyService  so it creates continuous‑flow sessions where orders are picked as they arrive, with dynamic slot assignment and re‑optimisation. Introduce multi‑step routes and workflows  – Replace one‑step pull rules with a configurable route editor that allows users to build sequences such as Receive  →  QC  →  Put‑Away or Wave Pick  →  QC  →  Staging  →  Consolidation  →  Packing  →  Shipping. Integrate this editor with the existing workflow engine so steps trigger at the correct time. Provide UI for dynamic route configuration  – Offer a graphical drag‑and‑drop editor, similar to the workflow builder, where users can design multi‑step routes with optional conditions, QC checkpoints, staging areas and consolidation logic. Enable dynamic re‑sequencing  – Use distance calculations, labour availability and equipment status to re‑optimise the sequence of picks and tasks as conditions change. Display suggested re‑sequence prompts to supervisors. 1 2 1.  2.  3.  4.  5.  1 Scope The scope of this enhancement includes: Front‑end changes to the picking module to allow selection of batch, cluster, wave and waveless strategies. Implementation of waveless picking logic in the  PickingStrategyService  and its handler, including continuous assignment of picks as new orders are received. Development of a route editor UI within the Warehouse  →  Routes section that supports multi‑step sequences with QC, staging, consolidation and other operational steps. Updates to the Routes and Workflow modules to support multi‑step routes and to link them to picking and put‑away operations through the workflow engine. Enhancements to display dynamic routing suggestions and re‑sequencing prompts based on real‑time data. The following are out of scope for this phase: 3D visualisation, labour‑management modules, multi‑client billing, and IoT integrations – these are addressed in separate phases. Assumptions The back‑end already supports batch, cluster and wave picking strategies via the  PickingStrategyService  and will be extended to support waveless sessions . The workflow engine can trigger put‑away and pick tasks through handlers . Roles and permissions are user‑defined; access control requirements are not specified here. The one‑to‑many mapping between functional areas and location codes is in place, enabling more granular assignment of picks. The default should be  Single  to maintain backward compatibility. When  Batch  or  Cluster  is selected, allow the user to set grouping criteria (e.g., destination, carrier, shipping cut‑off time). When  Wave  is selected, allow configuration of wave size and release cadence. When  Waveless  is selected, disable grouping controls and display a notice that tasks will be continuously assigned. Waveless Picking Logic 1.  2.  3.  4.  5.  6.  3 Implement continuous‑flow picking in  PickingStrategyService : upon creation, a waveless session listens for new reserved orders and automatically assigns pick tasks to the queue. Ensure pick tasks created during waveless sessions use real‑time distance calculations and labour availability to assign tasks to the nearest available worker. Provide an API endpoint for mobile clients to poll and retrieve the next task in the queue. Multi‑Step Route Editor Replace the existing one‑step route interface with a drag‑and‑drop editor modelled after the workflow builder. Users should be able to add steps (Receive, QC Inspect, Put‑Away, Cross‑Dock, Staging, Consolidation, Packing, Shipping) and connect them in sequence. Allow conditional branches (IF/ELSE) to handle scenarios such as damaged goods or cross‑dock triggers. Provide a canvas to reorder steps, delete steps, and configure properties (e.g., QC sampling rate, staging area). Persist the route definition as part of the route record and link it to workflow templates for execution. Integration with Workflow Engine Map each route step to a workflow step type recognised by the workflow engine (e.g., QC  → QC_INSPECT, Staging  →  STAGE). On execution, the workflow engine should call the appropriate handler (PickHandler, PutawayHandler, QCHandler) to generate tasks. Ensure that route definitions can be activated/deactivated and versioned. Dynamic Re‑sequencing and Monitoring Build a dashboard for supervisors showing active pick sessions, worker status, and travel distances. Integrate with the floor‑plan module to retrieve distances and with labour data to determine worker availability. Implement algorithms to suggest re‑sequencing (e.g., reassign tasks to idle workers) and present accept/reject options to supervisors. UI Enhancements and Accessibility Ensure the new forms and editors are responsive and accessible for both desktop and mobile users. Provide tooltips and inline help to explain picking strategies and route steps. Non‑Functional Requirements Performance:  Creating a picking session should take no more than 2 seconds. Waveless queues must assign new tasks within 1 second of an order being reserved. Scalability:  The system should handle at least 500 concurrent pick tasks and 20 simultaneous workers without degradation. Reliability:  Route definitions and picking sessions must persist across service restarts. Tasks should be idempotent to prevent duplication. Usability:  Drag‑and‑drop interactions must be intuitive; user testing should ensure that warehouse operators can configure a multi‑step route in under five minutes. Dependencies Extension of  PickingStrategyService  for waveless logic. Update to front‑end components (React/Vue) to support strategy selection and route editing. Integration with the existing workflow engine and handlers for QC, staging and consolidation. Mitigation: provide pre‑configured templates and contextual help. Performance overhead:  Waveless continuous flow and dynamic re‑sequencing may increase database and CPU load. Mitigation: optimise queries, cache frequently accessed data and monitor performance under load. Data consistency:  Ensuring that tasks are correctly created and closed across different steps requires robust transaction management. Mitigation: leverage existing transaction patterns in the workflow engine. Open Questions Should the grouping criteria for batch/cluster picking be limited to destination, product type and shipping cut‑off, or should users be able to define custom fields? How should the system prioritise between wave and waveless sessions when orders could belong to both categories? For example, should urgent orders bypass the current wave and be added to a waveless queue? What level of granularity should the re‑sequencing algorithm operate on – entire orders, individual lines or pick tasks? Would users prefer manual overrides or automated adjustments?
